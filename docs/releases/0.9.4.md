# 0.9.4 WorkBuddy 的对话也有跨度了，标题不再撞车

0.9.2 / 0.9.3 把时间轴上的对话画成了跨度条，但 WorkBuddy 的会话始终只有一个点；同时时间轴上出现好几行同名会话（`Play · Claude` 四行、`# AGENTS.md instructions...` 三行），看着像同一段对话被反复识别。

## 为什么 WorkBuddy 没有跨度

Claude 和 Codex 的采集器会把每条消息同步到服务端，服务端按消息时间戳聚合出 5 分钟活动桶——时间轴的跨度就是用这些桶画的。WorkBuddy 的采集器只上报「状态变化」（running / done），从不同步消息，活动表里没有它的任何数据，于是每条 WorkBuddy 对话只能退化成登记那一刻的一个刻度点。

## 为什么多个对话同名

核对本机 33 个 transcript 的首条提问后确认：**这不是重复识别，是不同的对话拿到了相同的标题**。

- WorkBuddy 的 transcript 只读尾部 8MB。大文件（有一个 18MB 的）落在开头的 `ai-title` 读不到，标题退化成尾部的注入块（`<cb_summary>`）或项目名兜底——于是几个不同对话都叫同一个名字；
- Codex 的标题直接取首条用户消息，而那条消息里塞的是 AGENTS.md 指令全文，于是好几行都以 `# AGENTS.md instructions` 开头。

## 修了什么

**采集端**

- WorkBuddy 采集器现在把 transcript 里每条消息、每次工具调用的时间戳聚合成 5 分钟活动桶，随状态事件一起上报。进行中的对话每轮都会静默补报（不产生通知），跨度不会停在第一轮；历史会话在登记时全文件扫一遍时间戳，第一次上报就带着完整跨度。
- 新文件先读头部 256KB 播种 `ai-title` / `custom-title` / `session-meta`，标题不再依赖尾部读取。
- 用户消息兜底标题剥离 `<user_query>` 包裹和 `>` 前缀；纯注入块（`<cb_summary>`、`<task-notification>`）不再被当成标题。
- Codex 解析 rollout 时跳过 `# AGENTS.md` 注入段，取真正的提问作为标题。

**服务端**

`POST /events` 接受可选字段 `buckets`（`{ at, count }[]`，单次最多 2000 条），落库到 `session_activity`（同一桶取较大的 count）。没有这个字段的老客户端行为不变。

## 升级

这一版**需要先升级服务端再换客户端**：跨度数据走 `/events` 的新字段，服务端不认识就会被忽略，WorkBuddy 的跨度不会出现（标题修复不受影响，它只改客户端）。

已经跑过一轮的 WorkBuddy 对话，在客户端升级后重新打开会话时会把整份 transcript 的时间戳补报一遍，历史跨度也能补上。

## 验证

- Rust 92 个测试通过（含 WorkBuddy 活动桶聚合、标题剥离注入块、Codex 跳过 AGENTS.md 的新测试），并用本机真实 transcript 做了兼容性扫描
- 服务端 130 个测试通过，新增 `activity-buckets.test.ts` 覆盖：桶落库、重复上报取较大值、非法 / 超量桶被丢弃
- 线上真实数据核对：31 行时间轴里所有 WorkBuddy 行为单点，且同标题行的首条提问互不相同
