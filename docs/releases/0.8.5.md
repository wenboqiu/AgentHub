# 0.8.5 手机端不再卡在旧状态

一个真实踩到的坑：Codex 在 Desktop 里早就跑完了（窗口只是开着），手机上那条会话还显示「运行中」，输入框灰着、按钮点不动，而且**永远**不变——不刷新、不重连、不消失。这种情况只能杀进程重开 App。

## 根因

不是服务端状态错了，是手机端的连接「假活着」。

Tauri 的 Android 端是 WebView，前端那条 WebSocket 在 App 切到后台、或者从 Wi-Fi 换到移动网络之后，常常既收不到消息、也**不会触发 `onclose`**：底层 socket 看着还是 OPEN，Chromium 只是把页面冻结了。原来的重连逻辑全靠 `onclose` 驱动，于是：

1. 服务端那边会话早就 `done` 了，但这台手机永远拿不到这条广播；
2. 前端一直拿着后台前的旧快照（那条 Codex 会话还是 `running`），`sendBlockReason` 据此把输入框和发送按钮锁死；
3. 没有回前台的刷新动作，也没有周期性重取，界面就定格在那一刻。

## 修了什么

**一、app 级心跳探活（前端 + 服务端）**

服务端每 30 秒发的协议层 `ping` 在浏览器 / WebView 的 JS 里是看不到的，没法用来判断连接死活。新增应用层协议：

- 客户端每 20 秒发 `{type:'ping'}`，15 秒收不到 `{type:'pong'}` 就判定这条连接已死，主动关掉重连（走原有 1s→30s 退避）；
- 服务端在 viewer 的 `/ws` 上回 `{type:'pong'}`；
- 兼容旧服务端：累计发了 3 次 ping 一次 pong 都没收到，就认为对端不支持，自动停掉心跳，只保留 `onclose` 兜底，避免旧服务端被反复掐连接。

**二、回到前台强制重连取新快照**

监听 `visibilitychange` / `online`：回到前台或网络恢复时，直接换一条连接（5 秒节流，避免窗口来回切换刷爆服务端）。服务端在连接建立时会推一份 `snapshot`，等于一次全量刷新——会话状态、任务、目标、提醒一起纠正。

**三、卡住的 `running` 不再永久锁死发送**

Codex Desktop 结束一轮时不一定会写终态：直接关窗口、进程被杀，日志尾部只留下 `task_started`。这时会话状态会永远停在 `running`，即使连接完全正常也发不出去。

现在服务端和客户端共用同一个阈值 `STALE_RUNNING_MS = 30 分钟`：`state=running` 但 `eventAt` 超过 30 分钟没有新事件，就不再拿它拦发送（发消息、分支两处都放行）。判定逻辑抽成 `src/lib/sendBlock.ts`，纯函数、单独测试。

## 验证

- 服务端 **109 个用例全绿**（新增 `remote.test.ts` 2 个：卡住 running 的 Codex 会话放行发送、viewer 的 app 级 ping 收到 pong）
- 前端 **13 个用例全绿**（新增 `test/sendBlock.test.ts` 4 个：正常运行仍拦、久无事件放行、阈值边界、其它阻塞原因不受影响）
- `tsc --noEmit`、`vite build` 通过

## 升级

服务端和客户端都要更新：服务端提供 pong，客户端才敢用心跳判死。先服务端、后客户端；只升客户端也能用（心跳会自动降级，回前台刷新仍然生效）。

注：Android 端要重新出包才生效。
