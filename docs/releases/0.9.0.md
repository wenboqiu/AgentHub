# 0.9.0 角色：谁来做、用什么模型、按什么准则

派活以前只有「用哪个执行工具」一个维度：Claude 还是 Codex，用哪台电脑、哪个目录。想换个模型、想让它按一套固定的准则做事（比如「只改前端，先读现有写法」「评审只挑毛病，不要重写」），只能在第一条消息里手写一遍，每次派活重复一次。

这一版把这三件事收成一个有名字的**角色**：

```
角色 = 执行工具 + 模型 + 上下文 + 可选默认配置
```

建好之后，发布任务时在「开始执行」旁边选一个角色就行——执行工具、模型、上下文一起生效。

## 角色和项目配置的分工

两个概念容易混，这里划清楚：

- **角色管人**：谁来做（claude / codex）、用什么模型、按什么准则（上下文）。
- **配置管地方**：哪台电脑、哪个目录、默认优先级、验收检查项模板。

角色可以挂一个默认配置。这样「前端实现」这个角色可以同时意味着：用 Claude、用 opus、只动前端代码、在 AgentHub 目录、验收要过 tsc 和 build。选角色，地方也一起带出来；但任务上显式填过的字段一律不覆盖。

## 上下文到底怎么送达

这是这一版在协议上真正做的改动。执行器的 `run.start` 以前只有 agent / cwd / text，现在多了两个字段：`model` 和 `instructions`。

- **Claude**：`--model <模型>` + `--append-system-prompt <上下文>`。走真正的系统提示，不污染第一条消息。
- **Codex**：模型用进程级配置覆盖（`codex -c model="…" app-server`，每个 run 一个进程，互不影响）；Codex 没有等价的系统提示钩子，上下文由执行器放在首条消息前面，用 `---` 分隔。

模型留空 = 用执行端自己的默认，不会强行覆盖。

## 老电脑端会怎样

不静默降级。执行器连接时用 `capabilities=reply-branch-v1,role-v1` 上报能力（原来只上报 reply-branch-v1，逗号列表也兼容老格式）：

- 电脑端支持 `role-v1`：正常执行。
- 电脑端还是旧的：照常派活（不会因为角色卡住），但接口会返回 `roleDegraded: true`，客户端当场提示「电脑端版本较旧：角色里的模型与上下文没有生效」。

服务端和客户端先升级不会坏事，但要让模型和上下文真正生效，电脑端也要升到 0.9.0。

## 排队也带着角色

离线排队（0.8.2）存的是「派给谁、发什么」的快照，这一版把模型和上下文也一起存进队列。这样排队期间改角色不会影响已经排上的那一活——上线后仍按入队那一刻的角色执行，测试里专门盯着这条。

## 用起来的顺序

1. 设置页 → 角色 → 新建：选执行工具、填模型（可留空）、写上下文、可选挂一个项目配置。
2. 打开任务 → 执行区 → 角色下拉选它（或者选好角色再点「开始执行」）。
3. 任务详情会显示当前角色的模型和上下文长度，避免「以为设了其实没设」。

## 验证

- 服务端新增 `test/roles.test.ts` 8 个用例：增删改查 / 同名拒绝 / 越权拒绝、建任务选角色补齐执行工具并带出配置、显式字段不被覆盖、派活时 `run.start` 带 model 与 instructions、老执行器降级标记、排队期间改角色不影响已入队的活、删角色后任务照常可用。
- 执行器新增两个单元测试：角色参数与原参数拼接（空角色时命令行逐字不变）、Codex 的模型与上下文通道。
- 全量服务端测试 117 个用例（新增 8 个）连跑三遍全绿；前端 `tsc --noEmit` 与 `vite build` 通过；`cargo check` 与 `cargo test --lib` 通过。

## 已知限制

- 角色上下文只在**新开**的派活里生效。会话续聊（在原会话里继续发消息）不会重新注入，这是 Claude 的系统提示按进程生效决定的；Codex 同理（上下文只加在首条消息）。
- 终端里开着的 Claude 会话（0.4.0 的投递通道）没有系统提示通道，角色上下文不会生效——但任务派活走的是新开会话，不受影响。
- Codex 的模型走的是 `-c model="…"` 进程级覆盖，需要 Codex Desktop 自带版本支持该全局参数；不支持时会在运行失败信息里直接暴露，不会静默走默认模型。
- 角色暂时不携带「允许哪些工具 / 权限模式」，那属于执行端的权限配置，后面再单独做。
