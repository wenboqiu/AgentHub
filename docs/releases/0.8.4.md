# 0.8.4 派活看板：排队、在跑、卡住，一眼看清

派活的手动链路到 0.8.3 已经齐了（选配置、离线排队、上线投递），但"派出去之后怎么样"要靠在任务列表里翻：哪个在跑、哪个排队等电脑、哪个其实已经没人管了，全都看不出来。0.8.4 把它们聚到一张**看板**上，异常当场给操作。

## 三个分区

顶部「看板」标签页，按健康度分组：

- **卡住**：任务状态是「进行中」，但既没排队、也找不到任何活跃执行。典型成因是目标电脑掉线把 run 打断后没人接手，或人为把状态改成了 doing。这是看板要抓的主要异常——不抓的话它会永远挂在那里。
- **排队中**：在队列里等目标电脑上线的活（0.8.2）。显示排队时间、尝试次数；电脑离线时标出来。
- **运行中**：有活跃执行的活。显示已跑时长、最后活动时间；有待授权时标「待授权」。

任务标签页的角标只数「待验收」，看板标签页的角标数「卡住」——两类需要人介入的事分开提示。

## 「在跑」怎么判定

一条 run 只要挂在任务上就算数，两条路都认：

1. `runs.task_id` 直挂任务（派活新开、手动计时都走这条）；
2. 经 `task_sessions` 找到关联会话名下的 run（在会话里续聊新建的 run 不写 task_id，只挂会话）。

两条路合并后取每个任务最新的活跃 run。这样不会把"在会话里接着跑"误报成卡住。

## 当场处置

- 卡住：**重新派发**（走 0.8.2 的派发链路，在线直发、离线重新入队）或**退回待办**（不派了，回到 todo）。
- 排队中：**立即派发**（手动派发优先于排队，队列里的旧快照作废）或**取消排队**。
- 运行中：点开任务详情看时间线、验收和摘要。

## 刷新时机

看板数据不落新表，全部现场推导。客户端在这些时刻重取：任务被 WS 推走一步、run 状态变化、执行器上下线。断线时保留上一次内容，不断自动刷新。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/dispatch/board` | 聚合条目 + 在线电脑列表，纯只读 |

条目字段：`taskId / title / status / agent / machine / priority / queued / attempts / queuedAt / run（活跃执行）/ waitingApproval / lastActivityAt / machineOnline / stuck`。

先升级服务端再升级客户端。无新表、无迁移。

## 已知限制

- 「卡住」只看活跃 run，不看活动时间：一个 run 挂着但 45 分钟无事件的情况由 Watchdog（0.6.0）按会话提醒，看板不重复判。
- 手动把任务标成 doing（没有 agent / 电脑）也会算卡住——这是有意的：doing 又没人跑就该有人决定派发还是退回。
- 看板不主动推送，靠事件触发重取；两台设备同时打开时各刷各的，最终一致。
