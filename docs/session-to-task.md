# 会话完成 → 任务单 → 派发

一条会话跑完后，不必再自己想着「接下来该做什么」。AgentHub 按三步走完：**系统整理建议 → 项目经理排成任务单 → 人确认后开工**。

```
会话 done
   │  /events
   ▼
处理意见 session_proposals   ← 规则档：最后一轮回复 + 证据链 + 未完成清单
   │  补执行人：原任务的角色 > 这个项目上做过最多的角色 > 唯一的角色
   ▼
任务单（可改标题 / 说明 / 验收要点 / 优先级 / 执行人 / 项目 / 执行边界 / 从哪开始）
   │  「让项目经理重写」可选：一次 run，用项目经理角色重排
   ▼
人确认 ──► 建任务（和手建任务同一条补值链）──► 派发
                                              ├─ 立即派发（在线直开、离线入队）
                                              └─ 只建任务，交给项目经理的自动派发
```

## 三个角色

| 谁 | 在哪 | 干什么 |
|---|---|---|
| 规则档 | `server/src/proposals.ts` `heuristicDraft` | 零成本拼装：原任务未完成项、失败测试、收尾语里的下一步 |
| 项目经理（细化） | `POST /proposals/:id/refine` | 用电脑上已登录的 agent 重写任务单，服务端没有模型凭据 |
| 项目经理（派发） | `server/src/dispatch-manager.ts` | 开关打开时，把「人已确认、还没派过」的任务按限额派出去 |

## 执行人是怎么定的

- **角色**决定「用什么工具、按什么准则做」；**配置**决定「在哪台电脑、哪个目录」。卡片上两者都显示，改角色时机器与目录跟着换。
- 规则档挑人的顺序：原任务的执行人 → 这个项目上做过最多活的角色 → 唯一的角色 → 留空由人选。**项目经理自己不当执行人**。
- 会话只记项目名，生成时会按名字对回项目编号，才能用项目历史挑人。

## 只留一张待确认

同一件事反复跑完（做完 → 被打回 → 又跑完）不会攒出好几张几乎一样的任务单：新意见落库时，同一任务上其它 `pending` 的旧意见自动作废（`discarded`）；会话还没挂任务时按会话收，免得一个会话里的两件事互相顶掉。已确认或手动忽略的不受影响，记录都还在库里。

细化档那一次 run 用的是**项目经理角色配的模型**（`roleModel`），不是执行工具的默认模型；角色没配才退回工具默认值。

## 对话流底部的入口

会话跑完后，聊天流最下方只留一个「任务单」入口（正文在详情页展开）。这个入口**只算还有意义的单子**：有待确认的报「N 份待确认」，都确认过的报「都已处理」。

- 被忽略（`discarded`）的单子不计入；一条会话的单子全被忽略时，入口整块消失，聊天流回到干净的结尾。记录仍然在库里，详情页能看到那张「这条建议不用了」的卡。
- 忽略会广播给所有窗口（`POST /proposals/:id/discard` → `{type:'proposal'}`），标签上的待确认数字当场跟着掉，不用等下一次拉快照。

## 忽略能撤回

忽略是「暂时不用」，不是删除：那张卡留在任务单详情页里，下面挂一个「撤回」，点一下回到 `pending`，入口和标签计数一起回来。

- 撤回只对 `discarded` 生效；`accepted` 的撤不回来——任务已经建好，撤回来只会和任务重复（接口返回 409）。
- 放回去也守「只留一张待确认」：同一任务（没挂任务时同一会话）上别的待确认意见照样作废，免得同一个活攒出两张单、被连点两次建出两个任务。
- 看板上刚被忽略的发单卡会多留一会儿（还是那张「这条建议不用了 · 撤回」），离开看板就不再列出来。

## 执行边界

任务单上还有一份「能碰哪」的声明（`tasks.constraints`）：能改哪些目录、能不能联网装包、能不能推远端、能不能跑脚本。

- 规则档生成的「接着做」会**沿用原任务的边界**，换个会话不悄悄放开；
- 细化档让项目经理按「这个任务真的需要什么」重新给，给不出就全空；
- 边界会拼进派发时的系统提示（`boundaryLine`），执行中超出边界的动作会停下来问人；
- 只在任务详情页手改也行——它是普通字段，不走模型。

详见 `docs/approval-referee.md`。

## 从哪开始：接着原会话，还是从零

同一件事有两种开场方式，卡片上可以选，项目经理也会先替人排一个：

| 方式 | 执行者拿到什么 | 什么时候合适 |
|---|---|---|
| **接着原会话**（`fork`） | 原会话的完整上下文，等于「同一个它」继续说 | 原任务没做完、回去修刚才那个报错 |
| **从零开始**（`fresh`） | 只有任务单里的说明、清单和项目近况 | 新的一段工作，上下文反而是负担 |

- **规则档**：`continue` / `fix` 给 `fork`，`followup` 给 `fresh`；项目经理细化时也可以在 `delivery` 里改。
- **任务上记一次**（`tasks.start_mode` / `fork_from`）：确认时写进去，派发时用掉就清回 `fresh`。所以「只建任务」之后项目经理自动派发，也会按同样的方式开场；而重试、重新派发不会又续回那个老上下文。
- **续不上的四种情况**会**自动退回新会话**，界面在点确认之前就会显示原因、把选项灰掉：

| 条件 | 为什么 |
|---|---|
| 原会话是豆包 / WorkBuddy / ZCode | 前两者只听状态、没有可续的会话；ZCode 没有按会话分叉的通道 |
| 执行人的工具 ≠ 原会话的工具 | 会话是各工具自己的，跨不过去 |
| 换了电脑 | 会话文件在那台机器上 |
| 任务目录 ≠ 原会话目录 | 相对路径、工作树状态都对不上 |
| 原会话还在跑 | 分叉一个正在写的会话没人能解释 |

判定分两层：会话这一侧能不能续由服务端给（`Proposal.fork`），跟执行人对不对得上由界面预览（`src/lib/delivery.ts`），真正派发时服务端按最终的工具 / 电脑 / 目录再算一次（`planDelivery`）并回传实际用的方式——所以卡上看到「接着原会话」，结果里也会这么写；中途换了执行人，结果里会说明为什么没续上。

离线排队也带着这个决定（`task_dispatch_queue.mode` / `session_key`），电脑上线后照原样开场。

## 自动派发的边界

1. 只派**由处理意见确认生成**的任务（`session_proposals.created_task_id` 指过去），历史 todo 一律不动；
2. 只派**没派过**的：没有活跃 run、不在排队、也没被自动派发成功过（确认时会挂来源会话，所以不能用「有没有关联会话」判断）；
3. 同一任务 24 小时内失败 3 次就停手；
4. 并发（默认 2）与每小时上限（默认 6）都按账号算，机器是同一台；
5. 没有「无人确认」的路径——任务必须由人在任务单上点过确认。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/proposals?sessionId=` | 待处理意见；带 `sessionId` 时返回该会话的全部 |
| POST | `/proposals/:id/refine` | 让项目经理重写（要求电脑在线） |
| POST | `/proposals/:id/confirm` | 确认建任务；`dispatch:false` 表示只建不发，`delivery` 可改成 `fork` / `fresh` |
| POST | `/proposals/:id/discard` | 忽略 |
| POST | `/proposals/:id/restore` | 撤回忽略：`discarded` 放回 `pending`；已 `accepted` 的返回 409（任务已经建好） |
| GET/PATCH | `/dispatch/manager` | 项目经理的角色、开关、并发与每小时上限 |

## 数据

- `session_proposals`：意见即任务单草稿（`role_id` / `profile_id` 存执行人，`delivery` 存打算怎么开场），`(user_id, session_id, event_at)` 唯一，一条会话多段完成可出多条。
- `tasks.start_mode` / `fork_from`：这个任务第一次派发时接着哪个会话；用掉即清，是「一次性的开场意图」而不是永久属性。
- `dispatch_manager`：一个账号一个项目经理。
- `dispatch_auto_log`：每次自动派发的留痕（dispatched / queued / failed + 原因）。
