# WorkBuddy 已读与 AgentHub 待处理同步

日期：2026-11-07。

原因：AgentHub 的 `acked` 只由自身的「已处理」按钮、新一轮运行、以及（Codex 专属的）已读回执更新。在 WorkBuddy 里看完一轮回复不会产生任何事件，待处理提醒就一直挂着，直到手动点「已处理」或 `done` / `aborted` 满 2 小时自动过期（见 [0.11.1](releases/0.11.1.md)）。用户明明已经读过，手机上却还显示「待处理」。

修复：电脑端每 15 秒只读核对 WorkBuddy 的已读标记 `~/.workbuddy/workbuddy.db` 里 `sessions.unread`（0 = 已读，1 = 未读），把「已经读过的那一轮完成」作为已读回执上报（带 `expectedAt` 与 `readAt`）。服务端只接受 Codex 与 WorkBuddy 两个 agent 的回执，且必须同账号、同机器、同一完成时间、同状态，只清 `done` / `aborted`，不动 `waiting`，也不改动标题和正文。

判定同时满足下面几条才算读过：

1. 这一轮在服务端还没确认（`acked = false`），状态是 `done` / `aborted`；
2. 库里那条会话 `unread = 0`；
3. 库里最后一次活动时间（`last_activity_at`）不晚于这一轮的完成时间（留 5 秒余量）——晚于它说明之后又动过，那个「已读」说的是新内容；
4. 库文件（含 `-wal`）的保存时间不早于完成时间——早于它说明清未读的那次写入发生在完成之前，不算证据；
5. 连续两次核对（间隔 ≥ 15 秒）结论一致。WorkBuddy 处理完一轮时，未读标记会有一小段还是 0，只看一眼就上报会误清。

库不在、表结构变了、文件被锁、解析失败，一律按「没有证据」处理，保持原状态。只读打开（`mode=ro`），从不写 WorkBuddy 的库。

实例对照（本机 `my-pc`，2026-11-07 实测）：`sessions.last_activity_at` 与服务端 `eventAt` 对同一轮完全相等（毫秒不差），`unread = 0` 的会话都是打开看过的，`unread = 1` 的都是自动跑完没人看的任务单监听会话——正好是「读过的不再提醒、没读过的一直等」两类。

验证：Rust 新增 6 项测试（已读清除待处理、未读保持提醒、库内活动更新的不算、库内无此会话不算、等授权/运行中/已确认的不动、快照早于完成时间不算、中途回到未读要重新攒两拍），`cargo test --lib` 122 项通过、4 项按设计跳过。服务端回执分支用假 pool 直跑 `applyEvent` 复核：WorkBuddy 回执清待处理且保留 title / summary，豆包回执被拒。服务端集成测试（`server/test/workbuddy-read.test.ts`）需要 Postgres，本机没有实例，未在本地跑。

生效需更新服务端和电脑端（Windows / macOS），Android 不用为此重新打包。更新后一般在两次轮询（≤ 30 秒）内清掉已核实的旧提醒。
